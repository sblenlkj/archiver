# Roadmap — Archive over VK

### 1. Ближайшее: переработать JavaScript collector

Переписать `collect_archive.js` и `collect_markdown.js` как более понятный, проверяемый компонент, а не одноразовый фрагмент для вставки в консоль:

- разобраться с `ConvoStack__content`, `ConvoHistory__messageWrapper`, `.MessageText` и реальным поведением DOM при прокрутке;
- отделить поиск группы, извлечение сообщений, сборку текста, диагностику и сохранение TXT;
- проверить порядок, полноту и отсутствие дублей, особенно при динамической загрузке/виртуализации;
- убрать хрупкие допущения и улучшить сообщение об ошибках; не считать текущую минимальную реализацию законченной;
- написать тесты на синтетических DOM-фикстурах и проверить большие многофрагментные сообщения;\n- усовершенствовать поиск последнего отдельного сообщения `###`, чтобы сборка не зависела от десятиминутного интервала и корректно работала при переходе между DOM-группами;\n- для Markdown сохранять точные переносы строк и копировать результат в буфер, для архива скачивать один Base64 TXT.

### 2. Надёжная доставка больших архивов: чанки и повторная отправка

**Идея, пока не реализована:** вместо одного неразмеченного Base64-текста добавлять индекс в конце каждого сообщения: до 4091 символа Base64 + суффикс вида `(001)` (в сумме до 4096 символов), до 999 частей.

- обнаруживать пропуски, дубли и нарушение порядка, даже если сообщения приходят с задержкой;
- фиксировать общее число чанков и идентификатор передачи, чтобы можно было определить отсутствующую последнюю часть и не смешивать архивы;
- выводить список отсутствующих индексов для выборочной повторной отправки;
- проверить, что ограничение по длине сообщения действительно допускает такой формат, и согласовать обработку неполного последнего чанка;
- сначала тестировать только на искусственных архивах.

### 3. Следующий эксперимент: Git и инкрементальная синхронизация

**Идея, пока не реализована:** передавать между двумя копиями учебного Git-репозитория **изменения между коммитами**, а не каждый раз полный архив.

Предполагаемая схема:

```text
source repo → фиксируем изменения/коммит
            → формируем Git-совместимый delta/bundle
            → кодируем в Base64 → тестовый текстовый канал
            → собираем и декодируем
            → проверяем базовый commit + целостность
            → применяем на второй копии репозитория
            → проверяем одинаковый итоговый commit/tree
```

Что изучить и проверить до реализации:

- выбрать между `git bundle`, `git format-patch` и другим форматом с учётом бинарных файлов, истории, переименований и конфликтов;
- как фиксировать/согласовывать `base commit` и целевой commit, чтобы не применять патч к неверной версии;
- критерии успеха: одинаковые commit SHA / tree SHA, корректная история, восстановление после пропущенного сообщения;
- когда создавать коммит автоматически, что делать с незакоммиченными изменениями и как сохранять возможность отката;
- Git-операции не должны молча переписывать пользовательские изменения; сначала тестирование на двух временных копиях учебного репозитория.

Это **будущий research/prototype**, не готовая функция.
